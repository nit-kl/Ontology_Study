# UC3　夕方の在庫融通と見切り

毎日の夕方、近くの店どうしで「閉店までに余りそうな商品」と「夜に品切れしそうな商品」を突き合わせ、ネットスーパー配送車の帰り便で余る店から足りない店へ移す流れです。期限が今日までで移せない商品は、電子棚札で時刻を決めて見切り値引きします。朝の UC1 で、イベントや暑さに備えて多めに発注した分が余りそうなときも、ここで回します。

前後: [UC2 電力ピークの自動調整](uc2-power-peak.md) / [ユースケース一覧](../usecase.md)

## 前提

| 項目 | 値 |
| --- | --- |
| 舞台 | 近くの3店。1号店（ST-014）、2号店（ST-031）、3号店（ST-040）。閉店は 22:00 |
| きっかけ | 毎日 16:00 の KINETIC のスケジュール |
| 見る商品 | 期限が今日か明日の日配品と惣菜 |
| 移すもの | B社 オーガニック牛乳（R-5581、期限は明日）20本を、1号店から2号店へ<br/>ヨーグルト（R-6120、期限は明日）55個を、3号店から2号店へ |
| 見切るもの | 3号店の弁当（R-8104、期限は今日）。19:00 から30%引き、20:30 から50%引き |
| 運ぶ車 | ネットスーパー配送車の帰り便。V-14（1号店の冷蔵車、2号店の地区の配達の帰り）、V-40（3号店の冷蔵車） |
| 承認する人 | 上限（50個かつ15,000円）以内の移動と、上限以内の見切りは不要。ヨーグルト55個は上限を超えるので、受け入れる2号店の店長 |
| 使う点検 | 在庫移動ルール（温度帯、期限、保冷時間、車の空き、ネットスーパーの引当分）、見切りの値引上限、承認 |
| 書き戻し先 | SAP（店間移動）、TMS（帰り便の立ち寄り）、店舗システム（スタッフ端末、POS、電子棚札） |

## 流れ

```mermaid
sequenceDiagram
    autonumber
    actor Manager as ① 2号店の店長<br/>(店舗タブレット)
    participant Kin as ② 現場手配ディレクター<br/>(Temporal)
    participant AI as ③ AI 提案<br/>(Bedrock + LangGraph / MCP)
    participant KG as ④ 商品・店舗ナレッジグラフ & ルール番人<br/>(W3C OWL / GeoSPARQL / SHACL)
    participant UI as ⑤ 承認画面 & 来歴<br/>(SHACL Form / W3C PROV-O)
    participant Sys as ⑥ 店舗・物流システム<br/>(POS・電子棚札・スタッフ端末 / SAP / TMS)

    rect rgb(240, 249, 255)
    Note over Manager,Sys: シーン1：夕方の在庫を突き合わせる（余る店と足りない店を探す）
    Note over Kin: 16:00 毎日のスケジュールで<br/>「夕方の在庫融通」ワークフローが起動
    Kin->>AI: 今日の融通と見切りの案を依頼
    AI->>KG: 近くの店、日配品と惣菜（期限の短い商品）、<br/>今夜のネットスーパー配送車のルートを問い合わせ [SPARQL Query / GeoSPARQL]
    KG-->>AI: 3店と対象の商品、帰り便 V-14・V-40 のルート
    AI->>Sys: 3店の店頭在庫（期限が今日・明日の分）と今日の販売数を確認 [POS API / MCP]
    Sys-->>AI: 牛乳 R-5581: 1号店 46本（ネットスーパー引当6本）/ 2号店 4本<br/>ヨーグルト R-6120: 3号店 80個 / 2号店 3個<br/>弁当 R-8104: 3号店 52個
    Note over AI: 閉店までの売れ行きを見積もる<br/>・牛乳: 1号店は22本余る / 2号店は 19:00 ごろ品切れ、20本足りない<br/>・ヨーグルト: 3号店は60個余る / 2号店は55個足りない<br/>・弁当: 3号店は35個余る。期限が今日なので移せない
    AI->>KG: 帰り便のルートから1km以内に受け入れる店があるか [GeoSPARQL]
    Note over KG: 【OWL + GeoSPARQL 推論】<br/>・V-14 は2号店の地区の配達の帰りに2号店の前を通る（0.3km）<br/>・V-40 は帰りに2号店の近くを通る（0.8km）
    KG-->>AI: V-14 は 17:50、V-40 は 18:10 に2号店へ立ち寄れる
    end

    rect rgb(238, 242, 255)
    Note over Manager,Sys: シーン2：ルールチェック。上限を超える移動だけ店長が承認
    AI->>KG: 融通と見切りの案の事前検証を依頼<br/>A. 牛乳20本: 1号店 ➔ 2号店（V-14）<br/>B. ヨーグルト55個: 3号店 ➔ 2号店（V-40）<br/>C. 弁当: 3号店で 19:00 30%引き、20:30 50%引き
    Note over KG: 【W3C SHACL 事前検証】<br/>✔ 在庫移動: 冷蔵の車、期限は明日（1日以上）、輸送20分（保冷2時間以内）➔ OK<br/>✔ 在庫移動: 1号店にネットスーパー引当の6本が残る（46 − 20 = 26）➔ OK<br/>✔ 見切り: 期限が今日、閉店の3時間前から、最大50% ➔ OK<br/>✔ 承認: A（20本・5,700円）と C は不要 / B は55個で上限超え ➔ 2号店の店長
    KG-->>AI: 事前検証 合格
    Note over KG: A と C は承認不要のため、そのまま確定<br/>➔ 店間移動 T-1601 と見切り M-1603 を登録 [SPARQL Update] ➔ 成功
    KG->>Kin: A・C の確定イベント
    AI->>UI: B の承認依頼
    UI-->>Manager: タブレット通知：「3号店からヨーグルト55個を 18:10 に受け入れ、<br/>今夜売り切る計画でよいですか？（夜の売れ行き見込み 58個）」
    Manager->>UI: 16:15 「承認する」をタップ
    UI->>KG: 承認付きのアクション要求
    Note over KG: 【W3C SHACL 再検証】同じ点検 ＋ 店長の承認 ➔ OK<br/>➔ 店間移動 T-1602 を登録 [SPARQL Update] ➔ 成功
    KG->>UI: 監査イベント
    Note over UI: 「16:15 2号店の店長が受け入れを承認」と、<br/>A・C を自動で確定した規則を記録 [W3C PROV-O]
    KG->>Kin: B の確定イベント
    end

    rect rgb(255, 241, 242)
    Note over Manager,Sys: シーン3：帰り便に積み、受け入れ、時刻どおりに値引きする
    Kin->>Sys: SAP: 店間移動伝票2件 / TMS: V-14 と V-40 に2号店の立ち寄りを追加<br/>スタッフ端末: 送り出す店に取り出し、2号店に受け入れと陳列の作業<br/>POS: 2号店の入荷予定
    Sys-->>Kin: 17:05 1号店のスタッフ端末「牛乳は18本しか見つからない」
    Kin->>AI: 数量の修正を依頼
    AI->>KG: T-1601 を18本に減らす事前検証（減らすだけなので承認不要）
    Note over KG: 【SHACL】✔ OK ➔ T-1601 を18本に [SPARQL Update] ➔ 成功
    KG->>Kin: 確定イベント
    Kin->>Sys: SAP の店間移動伝票と2号店の入荷予定を18本に
    Sys-->>Kin: 17:50 2号店で牛乳18本、18:10 ヨーグルト55個を受け入れ（スタッフ端末でスキャン）
    Note over Kin: 19:00 まで待つ（Temporal のタイマー）
    Kin->>Sys: 19:00 3号店の弁当を30%引きに [電子棚札 / POS]
    Kin->>Sys: 20:30 同じ弁当を50%引きに [電子棚札 / POS]
    Note over KG,UI: 移動、数量の修正、見切りの来歴が監査グラフに残る。<br/>閉店後の売れ残りと廃棄は、履歴の蓄積先から BI で振り返る
    end
```
