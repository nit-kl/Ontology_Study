# CPグループ店舗の空調オントロジー（1店舗サンプル）

[タイのCPオール](https://jp.investing.com/equities/cp-all-company-profile)が運営するコンビニ1店舗を型にした、学習用の架空データです。主題は、土曜の朝に空調と来店の状況を見て、現場の機器へ指令を出すことです。実在の店舗、実測、契約ではありません。外部APIは呼ばず、このPCの中だけで動きます。指令も画面の中だけで、実機へは送りません。

## 朝8時のシナリオ

モデル店舗は `7EL-BKK-SS01`、バンコク・パトゥムワン区の架空店です。基準時刻は 2026-10-10 08:00、土曜日です。室外機1台が、売場・バックルーム・倉庫の室内機へ冷媒を供給します。

この時刻の状況は次のとおりです。数値は業務DB、しきい値はグラフの方針です。

- 売場 27.8℃（設定 25℃、快適幅 ±1.5℃）。来店は直近1時間 86人で、平常の 50人を超えている。
- バックルーム 26.3℃（設定 26℃）で快適範囲内。
- 倉庫 29.6℃、湿度 76% で上限 70% を超えている。運転モードは冷房。
- 外気 33.2℃。予報は 9時 34.1℃、10時 35.0℃。
- 室外機の電力 6.9 kW、定格冷房 7.1 kW。
- 入口ドアの開放率は直近15分で 0.40。エアカーテンはオフ。
- 売場の室内機と排気ファンの風量は中。売場室内機の運転時間は 2140時間で、点検間隔 2000時間を超えている。

デモが出す指令は次の5件です。フィルタ点検は作業指示として分けます。

| 対象 | いま | 指令 | 戻す条件 |
| --- | --- | --- | --- |
| バックルームの室内機 | 設定 26℃ | 27℃ | 来店が平常の 50人以下に戻ったら 26℃ |
| 売場の室内機 | 設定 25℃ / 風量 中 | 設定は 25℃ のまま、風量を強 | 売場が快適幅に戻ったら風量を中 |
| 倉庫の室内機 | 冷房 | 除湿 | 湿度が 70% 以下になったら冷房 |
| 入口エアカーテン | オフ | オン | ドア開放率が 25% を下回ったらオフ |
| 売場の排気ファン | 風量 中 | 弱 | 外気が 32℃ を下回ったら中 |

## 標準オントロジー

[`ontology/cp-retail.ttl`](ontology/cp-retail.ttl) は、次の語彙を IRI で参照します。全文は同梱していません。

| 語彙 | このサンプルでの役割 |
| --- | --- |
| Brick 1.4 | 空調システム、ヒートポンプ、ファンコイル、ファン、ゾーン、センサー、設定温度、時系列ID |
| BOT | 敷地、建物、階、空間、建物要素 |
| SOSA | センサーが温度・湿度・電力などの量を観測すること |
| QUDT | 単位（℃、kW、kWh、時間）と定格冷房能力 |
| schema.org | 運営組織、住所、営業時間 |

ローカル語彙 `cpr:` は、快適幅、点検間隔、指令方針、業務DBとの列対応です。エアカーテンは Brick 1.4 に安定したクラスがないため、`brick:Equipment` と `bot:Element` のサブクラスにしています。`owl:imports` は宣言しており、デモの rdflib はインポート先を取得しません。グラフDBへ載せるときに Brick、BOT、SOSA、QUDT を一緒に読むと、型の整合を検証できます。

## グラフと業務DB

グラフに置くのは、関係と、めったに変わらない方針・仕様です。設定温度は Brick の `brick:value`、定格は QUDT の数量、朝のしきい値は `cpr:DispatchPolicy` です。

変わる数は SQLite です。

| 表 | 中身 | 結合 |
| --- | --- | --- |
| `point_reading` | 温度、湿度、電力、電力量、発停、運転時間、風量の段、エアカーテンの発停 | `store_code` と `brick:hasTimeseriesId` |
| `footfall` | 直近1時間の来店人数 | `store_code` |
| `door_interval` | 直近15分のドア開放率 | `store_code` |
| `weather_forecast` | 先2時間の外気温 | `store_code` |
| `equipment_mode` | 室内機の冷房 / 除湿 | `store_code` と `equipment_code` |

## 起動

```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install -r requirements.txt
.\.venv\Scripts\python scripts\init_db.py
.\.venv\Scripts\python scripts\serve.py
```

ブラウザで <http://127.0.0.1:8765> を開きます。サーバーは `127.0.0.1` だけで待ち受けます。

確認:

```powershell
.\.venv\Scripts\python scripts\check_demo.py
```

## デモで見られること

画面を開くと、店舗の状況、5件の機器指令、フィルタの作業指示、ゾーンと機器の根拠が出ます。エージェントは質問の意図を選び、`queries/` の SPARQL と固定の SQL だけを実行します。質問文からクエリは作りません。

- 朝の機器指令（いまの値、変える値、根拠、戻す条件）
- 空調構成（組織、BOT の空間、Brick の機器、エアカーテン）
- 設定温度から外れているゾーンと、湿度の上下限
- 累積運転時間が点検間隔を超えた室内機
- 標準語彙と業務DBの役割分担

## グラフDBへ載せるとき

TTL が正本です。Apache Jena Fuseki なら、ローカルで次のようにメモリへロードできます。標準オントロジー本体も同じストアへ入れると、サブクラスの推論に使えます。

```text
fuseki-server --mem --file=ontology/cp-retail.ttl /cp-hvac
```

デモの読み取りは `src/graph_store.py` の `KnowledgeGraph` に集まっています。ここを SPARQL エンドポイントへの送信に差し替えれば、クエリファイルと画面はそのまま使えます。測定列と来店などの状況は SQLite のまま、店舗コードと時系列IDで結合します。
