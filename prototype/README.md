# デモ用プロトタイプ: UC1〜UC3

[ユースケース](../usecase.md) の3つの場面を、5つの層に分けたまま手元で動かすプロトタイプです。RDF、OWL、SHACL、SPARQL、GeoSPARQL、PROV-O、ODRL は本物の W3C 標準のライブラリで動きます。クラウドのサービス（Bedrock、SageMaker、Temporal、SAP、BMS、TMS など）は、同じ役をする小さな代役に置き換えています。

| シナリオ | 日付 | 起きること |
| --- | --- | --- |
| [UC1 明日の発注と需要予測](../usecases/uc1-forecast.md) | 2026-10-23（金）10:00 | 明日の試合・暑さ・新商品に合わせて1号店の発注を増やす。氷が置き場に入らない案を SHACL が止め、推奨数の1.5倍を超える3品を店長が承認。DC の在庫不足で数量を直す |
| [UC2 電力ピークの自動調整](../usecases/uc2-power-peak.md) | 2026-08-07（金）12:30 | 何もしないと 830kW の予測に対し、霜取り・予冷・空調・照明を方針の順に足して 758kW に。承認は不要。14:20 に窓際の売場が 27.2℃ になり、AHU-2 だけを戻す |
| [UC3 夕方の在庫融通と見切り](../usecases/uc3-evening-transfer.md) | 2026-10-23（金）16:00 | 3店の余りと不足を突き合わせ、帰り便で牛乳とヨーグルトを2号店へ。上限を超えるヨーグルトだけ2号店の店長が承認。17:05 に牛乳が18本しかなく数量を直す。弁当は 19:00 と 20:30 に見切り |

UC2 は資料どおり暑い夏の日にしたので、UC1・UC3 とは日付が違います。司令塔でシナリオを選ぶと、その日付と元データで最初から始まります。

## 動かし方

Python 3.11 以上と Node.js 20 以上が要ります。

```sh
cd prototype
python -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt      # macOS / Linux は .venv/bin/python

# 画面をビルドする（TypeScript + Vite。web/dist に出力され、FastAPI が配信する）
cd web
npm install
npm run build
cd ..

# サーバーを起動して http://127.0.0.1:8000 を開く（司令塔）
.venv/Scripts/python -m uvicorn app.server:app --port 8000

# 画面なしで最後まで流す / テスト
.venv/Scripts/python run_demo.py            # UC1。uc2 / uc3 を付けるとそのシナリオ、--detail で各出来事の中身も
.venv/Scripts/python -m pytest -q
```

画面を直しながら動かすときは、サーバーを 8000 番で起動したまま `web` で `npm run dev` を実行し、Vite の開発サーバー（http://localhost:5173）を開きます。`/api` は 8000 番に渡されます。

## 画面

司令塔の上の段でシナリオを選び、右上のボタンで進めます。時刻を進めるボタンには「▶ 自動で進める」が付いていて、押すと1秒ごとに次の時刻へ進みます。画面は役割ごとに分かれていて、司令塔の「画面を開く」からそれぞれ別のウィンドウで開けます。どの画面で操作しても、ほかの画面に1秒ほどで反映されます（各画面が `/api/revision` を見張っている）。

## 層と、このプロトタイプでの実装

| 層 | 資料での実装候補 | このプロトタイプ | ファイル |
| --- | --- | --- | --- |
| レイヤー1 基幹システム | SAP、POS、WMS、スタッフ端末、BMS、TMS、外部データ | ファイルから読んでメモリに持つシミュレーター。書き戻しを受け付け、WMS は在庫が足りなければ断る。BMS は時刻つきの設定を当て、5分ごとに設備・温度・デマンドを計算する。画面はわざと古い見た目にしてある | `app/layer1.py`、`data/layer1/`、`web/l1/`、`web/src/l1/` |
| レイヤー2 セマンティックETL | RML + Morph-KGC、Kafka | 列と述語の対応表（`MAPPINGS`）を宣言し、小さな実行係が三つ組にする。BMS の計測値はストリームとして最新の観測を差し替え、書き戻し後の SAP の変更は CDC として読む | `app/layer2_etl.py` |
| 履歴の蓄積先 | データレイク | 1号店の過去8週間の販売明細の CSV（生成スクリプトつき）。UC2 の計測値もデモの間はここへ追記する | `data/lake/`、`scripts/generate_history.py` |

| レイヤー3〜4 確定の窓口 | SHACL → SPARQL Update → 監査・確定イベント | アクションの中身（発注の明細、設備の設定、店間移動、見切り）を問わず、SHACL に合格したものだけを SPARQL Update で書き込み、PROV-O の来歴と CloudEvents の確定イベントを出す | `app/action_gate.py` |

## ナレッジグラフの中身

| ファイル | 中身 |
| --- | --- |
| `knowledge/ontology.ttl` | 種類、SKOS の区分、OWL のプロパティの連鎖（商品 → 区分 → よく売れる事情 → イベント、センサー → 区画 → 空調機、UnifiedSKU から卸側と小売側のコード）、「ピークに動かせる設備」の定義（動かせる幅を持つ設備）、Brick に合わせた設備の種類、発注・電力ピーク・在庫融通・見切りの方針 |
| `knowledge/shapes.ttl` | UC1 の点検: 数量の形、発注の単位、置き場の容量、予測の範囲、予測の出どころ、似た商品 |
| `knowledge/equipment_shapes.ttl` | UC2 の点検: 動かせる設備、霜取りの間隔（日をまたぐ間隔も）、食品安全（見込み）、売場の快適性（見込み） |
| `knowledge/transfer_shapes.ttl` | UC3 の点検: 在庫移動の温度帯・期限・保冷時間・車の空き・引当分・帰り便（送り出す店の車か、ルートが受け入れる店から1km以内か。GeoSPARQL）、見切りの値引上限 |
| `knowledge/approval_shapes.ttl` | 承認の点検: 推奨数の1.5倍を超える発注、自動の範囲を外れる設備の調整、上限を超える店間移動。承認者が ODRL でその権限を持つかも見る |
| `knowledge/monitor_shapes.ttl` | UC2 の実行中の見張り: 売場の温度（受け持つ空調機を推論して返す）、ケースの庫内温度 |
| `knowledge/policy.ttl` | ODRL の権限。店長ごとに、発注・設備の調整・店間移動の受け入れを承認できる店 |

## 本物の構成との違い

- AI エージェントは生成 AI を呼びません。判断の手順を固定しているので、毎回同じ結果になります。Bedrock に置き換えるときは、各エージェントの案づくりと直しの判断を、ツール呼び出しつきのモデルに任せます。
- 数字は資料の例と少しずれるところがあります。UC1 の予測は 107・37・115・51（資料は 105・36・118・52）ですが、ケースの倍数に丸めた発注数は資料と同じです。UC2 の調整後の見込みは 758kW（資料は762）、実績の最大は 776kW（資料は785）です。UC3 は資料と同じです。
- UC2 の霜取りは、日をまたぐ間隔も8時間以内になるよう 02:00 にも1回入れています（資料は 08:00・14:00・20:00 の3回）。
- KINETIC は状態をメモリにだけ持ちます。Temporal のように、止まったあとに続きから再開する機能はありません。
- ストア、監査グラフ、基幹システムの状態は、サーバーを止めるか、リセットやシナリオの切り替えをすると消えます。
